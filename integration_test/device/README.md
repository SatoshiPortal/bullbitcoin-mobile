# Exchange credential probes on physical Android devices

These probes are maintained regression tests to rerun when credential storage, transport authentication or WebView authentication changes.

These standalone tests use the real Dio, WebSocket and WebView plugins over an in-memory `ExchangeCredentialStorage`. Credentials live in the app's encrypted Exchange database, which a standalone probe cannot open, so the probes check the transport, WebView and error-propagation behaviour that surrounds the store, not the store itself. They do not initialize wallets or submit exchange orders. The simulated storage refusal checks error propagation; it does not claim to reproduce a keystore failure.

1. Reserve the physical device and verify its installed application ID, signer, configuration and available space. Save the installed debug APK(s) and their version code for final restoration. Use the project's pinned SDK and the host's configured Android SDK, JDK and ADB server. Preserve the existing debug application's data.
2. Run `make exchange-credentials-device-build`. The output is `build/app/outputs/flutter-apk/app-arm64-v8a-production-debug.apk`, for `android-arm64` only.
3. Verify the APK's application ID is `com.bullbitcoin.mobile.debug` and its signer matches the installed debug application. Install in place with `adb -s <serial> install -t -r <apk>`, explicitly selecting the shared ADB server when applicable. Stop on installation failure; do not uninstall or clear data to recover automatically.
4. Launch the debug main activity and forward its reported Dart VM service port to an available localhost port. Run `make exchange-credentials-device-test VM_SERVICE_URL=<forwarded-service-uri>`. `VM_SERVICE_URL` selects the application under test; the driver does not select an ADB device. The SDK integration driver connects directly to that VM service; it does not install, uninstall or stop the application. Avoid `flutter test` here: its integration runner uninstalls by default and its install fallback can also uninstall an existing app.
5. Stop the test application, then install the normal debug application with the same signer and an in-place install. Verify the existing session and normal account/wallet screens. Finally restore the saved original APK(s) and verify the session again before locking and releasing the device. ABI splitting can increase the APK version code; if the saved original has a lower code, use `install -t -r -d` only after confirming both applications are debuggable and have the same signer. This preserves app data and avoids leaving an elevated version code that could obstruct later development installs. Remove the task's own ADB port forwarding.

These files stay below `integration_test/device/` so the ordinary top-level integration aggregator does not discover device/session-dependent probes.

The loopback HTTP/WebSocket probes use Dart I/O, without changing platform network-security settings ([Flutter network policy](https://docs.flutter.dev/release/breaking-changes/network-policy-ios-android), checked 2026-10-20). Native instrumentation reporting is disabled for this VM-service-driven harness.

## Retained-balance startup probe (real application)

Use the normal `lib/main.dart` entry point, not an integration-test entry point. Build only a debuggable production-flavor arm64 APK with the pinned SDK (`fvm flutter build apk --debug --flavor production --target-platform android-arm64 --dart-define=BULL_BALANCE_STARTUP_HARNESS=true --dart-define=BULL_BALANCE_HOLD=true`). The second define holds the first balance demand outside the shell. The probe does not exist in release or in debug builds without the first define. It does not replace Access, Preferences, catalogue or native runtime.

Before installation in a separate authorized run, reserve a development device, check the debug application ID and installed signing certificate, and verify the APK's effective endpoints and the active Regtest network (Scuttle preferred). Use an isolated Regtest profile with already initialized Bitcoin and Liquid stores; never use a primary profile or real funds. If there is no isolated profile, signer mismatch, or uncertainty about the network, stop; no clearing data, uninstall, or bypass. Retain the original compatible APK for in-place restoration as described above.

Connect only through a loopback VM-service forward for that device. Use the `ext.bull.balanceStartup` service extension on the main isolate (through the authenticated VM service). With no parameters it returns counters; `action=hold` blocks further demands before Sync, `action=release` releases them. It returns only aggregated counts (`armed`, `initialized`, `initRefused`, `blocked`, `invalidations`, `attempted`, `retained`, `refused`, `bitcoinRetained`, `liquidRetained`) and `held`, not keys, amounts, paths, or credentials. Absent counters mean zero. Treat the VM service URI as private; do not publish it or leave the port forward running.

1. On a protected cold start, inspect the counters before and after an incorrect PIN (`armed` and `attempted` remain zero). After the correct PIN, the shell must become usable with a demand held (`blocked` increases, `attempted` remains zero, `initialized` is one). Release it and check both chain counters on already populated local stores before relying on any sync outcome. If the stored balances cannot be distinguished from a network update in that setup, report that limit; visible Home values still come from the legacy reader and are not evidence. Repeat cold start with a separate unprotected test profile.
2. At a non-Home URI (include a query where applicable), hold the next demand, trigger a harmless catalogue label change while native sync is idle, lock, and unlock with the correct PIN. Verify the previous URI returns while demand is still held. Release in a separate step and verify the retired demand did not increment the completion count and the new demand did. Repeat with immediate re-lock and with a changed native revision on each chain. Keep the multiview gate disabled. The probe intentionally cannot inject a failure into durable native initialization; the Linux fixture covers the `Err` path.
3. Report the build SHA, debug ABI, effective Regtest profile, count deltas and what was not verified. Restore the normal APK only in place with a compatible signer, remove the forward, lock the phone, and release the reservation. Do not capture PINs or secrets in screenshots, logs or semantics dumps.
