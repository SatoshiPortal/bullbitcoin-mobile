# background_tasks

Headless scheduling infrastructure, ported from the unshipped #3058. This phase does not activate work or register an application graph. Flutter is used only for platform services/plugins; no widgets or foreground SyncCoordinator belong here.

WorkManager resolves the task before calling bootstrap; the runner receives that typed task without resolving it again. Unknown tasks and the obsolete swaps task are acknowledged without building a graph. Bootstrap receives the selected BackgroundTask. BackgroundTasksLocator.setup invokes only that task's factory; each acquired resource must register its cleanup immediately with BackgroundTaskResources.onClose. Cleanup runs in reverse order after execution or partial startup failure, attempting all closes even if one fails. A wallet factory must check the application schema before opening its database and must construct only catalog, connection policy, writer, queue and notification capabilities. The application supplies factories and binds the consumer port to the writer during integration; no application graph is supplied in this phase.

SqliteWalletSyncJobQueue accepts WalletRevision values keyed by WalletKey, with typed networks and chains. It persists the generation/revision pair, never a fixed source revision. A disabled job becomes eligible when that pair changes. The caller must obtain authoritative stamps from WalletRevisionReader; unavailable or pending revisions must not be interpreted as removal. The failure's stamp must correspond to the writer operation that failed, rather than an arbitrarily old pre-admission read.

The queue preserves bounded exponential backoff, expiring and renewable claims, stable insertion order, and fairness across interrupted and successful wallets. Lease tokens guard completions against stale workers. These leases schedule work; they do not own or release the native writer lock. The database contains hashed wallet identities, typed network categories encoded for storage, version pairs, counters and timestamps. Queue diagnostics contain only categories and counts.

The queue is rebuildable scheduling state, unlike the notifications outbox. No compatibility is owed to #3058's unshipped queue. Losing queue state loses retry/fairness history but must never lose payments or authorize overlapping native writes.

BackgroundWalletSync is this package’s consumer-side port; the integrator binds it to transaction_sync’s writer. It returns a committed WalletRevision, the complete incoming txid set (for replay after an interrupted handoff) and completion time. Amount and confirmation state are deliberately omitted because the outbox uses payment identity only. Needs-repair failures carry the stamp observed under writer ownership. WalletTransactionSyncBackgroundTask reads authoritative revisions before every admission, requests allowInitialScan:false, renews its queue lease and persists notification observations before acknowledging success. Jobs run sequentially, with a per-chain job cap and Bitcoin’s half-budget admission limit. A lease loss stops subsequent admissions. Unsupported networks stay disabled until their revision changes; initial scans wait for the foreground without a retry storm. The writer binding records WalletSyncCompletion through notifications’ WalletPaymentObservationAdapter before returning a successful BackgroundSyncOutcome. The completion captures discoveries and foreground visibility; revision reloads never invoke the adapter. The original runner's admission budget was not a completion timeout: a native operation already started may outlast it. No timer may release the native lock. Android engine teardown/contention/process-death validation and iOS expiration validation remain required before activation.

Integration needs the two package workspace entries and dependencies in the root manifest/lockfile. Package plugin constraints are ported from #3058 (workmanager ^0.10.10 and flutter_local_notifications ^22.3.0); the root lockfile has not been changed by this lane.

The first foreground completion silently establishes the full incoming-history baseline, but marks only its own discoveries seen. Background runs before that baseline are deliberately silent. Once initialized, full incoming observations replay missed outbox handoffs without turning background payments into foreground discoveries. Foreground visibility/provenance must be captured by the writer binding, not sampled later by a screen reload. A process death before the first baseline retains the same explicit silent-initialization policy; no exactly-once foreground provenance guarantee is claimed across that boundary.

BackgroundTaskLogger is the shared persisted diagnostic sink for runner, queue and task. Claims and completions use fine; recoverable failures use warning with exception types only. Interval persistence returns a typed failure when the platform cannot save the choice.
