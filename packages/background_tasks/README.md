# background_tasks

Headless scheduling infrastructure, ported from the unshipped #3058. The app integration is present behind `backgroundSyncEnabled = false`; it does not register any periodic work until a maintainer enables the switch after device validation. Flutter is used only for platform services/plugins; no widgets or foreground SyncCoordinator belong here.

WorkManager resolves the task before calling bootstrap; the runner receives that typed task without resolving it again. Unknown tasks and the obsolete swaps task are acknowledged without building a graph. Bootstrap receives the selected BackgroundTask. BackgroundTasksLocator.setup invokes only that task's factory; each acquired resource must register its cleanup immediately with BackgroundTaskResources.onClose. Cleanup runs in reverse order after execution or partial startup failure, attempting all closes even if one fails. A wallet factory must check the application schema before opening its database and must construct only catalog, connection policy, writer, queue and notification capabilities. The app supplies task-specific factories in `lib/background_bootstrap.dart`; no `AppLocator` or Secrets graph is constructed.

SqliteWalletSyncJobQueue accepts WalletRevision values keyed by WalletKey, with typed networks and chains. It persists the generation/revision pair, never a fixed source revision. A disabled job becomes eligible when that pair changes. The caller must obtain authoritative stamps from WalletRevisionReader; missing, busy or pending revisions are returned separately from ready stamps, remain present in the queue without resetting retry state, and do not prevent healthy wallets from being admitted. Deleted wallets are still removed; invalid catalog and unclassified storage failures still abort selection. The failure's stamp must correspond to the writer operation that failed, rather than an arbitrarily old pre-admission read.

The queue preserves bounded exponential backoff, expiring and renewable claims, stable insertion order, and fairness across interrupted and successful wallets. Among due jobs, the oldest next-attempt time precedes the attempt count, so overdue retries cannot be permanently outranked by recently successful wallets. Lease tokens guard completions against stale workers. These leases schedule work; they do not own or release the native writer lock. The database contains hashed wallet identities, typed network categories encoded for storage, version pairs, counters and timestamps. Queue diagnostics contain only categories and counts.

The queue is rebuildable scheduling state, unlike the notifications outbox. No compatibility is owed to #3058's unshipped queue. Losing queue state loses retry/fairness history but must never lose payments or authorize overlapping native writes.

BackgroundWalletSync is this package’s consumer-side port; the wallet feature binds it to transaction_sync’s writer. It returns a committed WalletRevision, the complete incoming txid set (for replay after an interrupted handoff) and completion time. Amount and confirmation state are deliberately omitted because the outbox uses payment identity only. Needs-repair failures carry the stamp observed under writer ownership. WalletTransactionSyncBackgroundTask reads authoritative revisions before every admission, requests allowInitialScan:false, renews its queue lease and attempts notification observation persistence without turning a committed sync into a failure. Missing observations remain distinct from empty history; later successful syncs replay the complete incoming set. Jobs run sequentially, with a per-chain job cap and Bitcoin’s half-budget admission limit. A lease loss stops subsequent admissions. Unsupported networks stay disabled until their revision changes; initial scans wait for the foreground without a retry storm. The writer binding captures visibility at completion; recoverable observation failure logs a fixed-category warning and preserves the committed sync result. Programmer Errors propagate to the task boundary. The completion captures incoming history and foreground visibility; revision reloads never invoke the adapter. The original runner's admission budget was not a completion timeout: a native operation already started may outlast it. No timer may release the native lock. Android engine teardown/contention/process-death validation and iOS expiration validation remain required before activation.

Integration needs the two package workspace entries and dependencies in the root manifest/lockfile. Package plugin constraints are ported from #3058 (workmanager ^0.10.10 and flutter_local_notifications ^22.3.0); the root lockfile pins the integrated versions.

The first foreground completion silently establishes the full incoming-history baseline without seen marks. Later foreground completions mark only payments absent from the stored set as newly seen; existing background payments retain their provenance. Background runs before that baseline are deliberately silent. Once initialized, full incoming observations replay missed outbox handoffs without turning background payments into foreground discoveries. Foreground visibility/provenance must be captured by the writer binding, not sampled later by a screen reload. A process death before the first baseline retains the same explicit silent-initialization policy; no exactly-once foreground provenance guarantee is claimed across that boundary.

Notification startup is optional: an unavailable outbox or failed platform initialization closes any partially acquired notification storage, logs a bounded warning and lets wallet synchronization continue without observation or delivery. Later successful runs replay complete incoming history into an existing baseline; they do not fabricate an empty history or recreate lost outbox state.

BackgroundTaskLogger is the shared persisted diagnostic sink for runner, queue and task. Claims and completions use fine; recoverable failures use warning with exception types only. Interval persistence returns a typed failure when the platform cannot save the choice.

## App rollout

`backgroundSyncEnabled` is an explicit source switch, OFF by default. Both scheduling and the headless entrypoint enforce it. Startup cancels the known legacy Bitcoin/Liquid/swaps jobs and the wallets/log-prune schedules while OFF; it does not call `cancelAll`. The app hides the interval and payment-permission controls while OFF. Foreground observation wiring is absent while OFF: no outbox is created and no payment-history enumeration runs. No permission prompt occurs implicitly.

When enabled, this app integration supports Android and iOS only. The default interval is one hour. The settings controls choose the interval, explicitly request notification permission, or open system notification settings. Actions are serialized, so an Off selection made while another action is pending is persisted and cancels scheduling afterward rather than being discarded. Desktop scheduling stays disabled: running headless logging and mobile-only notification initialization inside the desktop foreground isolate is not supported. The generic timer scheduler remains available to other hosts.

Headless admission refuses missing initialization, pending writes and post-repair state under the writer lock. It never provisions, repairs or reconciles stores; those states wait for the next foreground app open. Bitcoin initial scans are deferred before a durable write intent is recorded. Native work already admitted is always awaited, even if it exceeds the admission budget. Real-device writer lifetime, process death/contention and iOS expiration checks remain required before enabling the switch.
